# tldraw/Yjs 内存实测与维护方案

日期：2026-11-07。分支：`codex/tldraw-yjs-scheme-a`。本轮只新增研究脚本、隔离测试页面、原始数据与文档；未修改产品映射、历史策略或云端数据。

## 结论

优先限制历史保留，再在安全空闲边界回收已释放内容。当前固定记录集合的移动/富文本负载不支持按固定时间重建整个共享文档：普通回收后，新树重建只额外节省约1–12KB，却有旧离线更新丢失风险。

首版候选：最近200个完整用户操作，加4MiB保留旧值JSON软预算，undo/redo一起计入；先触达者触发淘汰。以上是由本轮负载推导的试验初值，不是已验证的跨设备内存上限。回收优先在操作结束、空闲约2秒时执行；整文档重新加载放在下一次打开或明确维护边界。

## 环境、负载与指标

- Windows x64；i7-14700HX，28逻辑核，约16GB RAM；Node24.14.0/V8 13.6.233.17-node.41；Yjs13.6.30；tldraw4.5.3。
- 主数据：100或4000个geo图形，每个包含约80字符标签。4000对应当前原生编辑器默认每页上限。没有图片/视频大值。
- 位置主实验：0或30000次`x/y`更新；每60次更新一个手势，共500个历史步骤。一个手势操作一个图形，再轮换下一图形；大组共改到500/4000个图形，不能理解成每个图形都修改30000次。
- 富文本补充：3000次2048字节ASCII文本原子替换；60次/步，共50步。前50个图形的当前正文也会变长，控制组和清理后的副本保留同样当前内容。
- 每条件运行3个全新Node进程，位置18次、富文本12次，共30次。依赖预热后测空载；每个采样等待25ms让RAF shim回调结束，再主动V8 GC三次。
- 使用真实Store、Y.Doc、生产binding/history适配器和实际HistoryManager，原生undo/redo栈与pendingDiff断言为空。Node没有完整Editor、DOM、Liveblocks、IndexedDB。
- 同时记录`heapUsed`、RSS、external、arrayBuffers、完整编码字节、gzip字节、JSON字节、历史步骤、CRDT结构/clock计数及保留旧值字节。
- 主要堆指标为`heapUsed − 同进程依赖空载heapUsed`；修改增长为`修改后heapUsed − 本次加载后heapUsed`。不是文件大小、RSS或整个浏览器内存。arrayBuffers已经包含在external，不重复相加。
- 下列数字取3次中位数，范围为最小至最大；不是置信区间。脚本与两个原始文件的SHA256一致性由分析过程断言。

## 四组主实验

- 少量、仅加载：100图形，相对空载保留堆 **1.44MiB**，范围1.40–1.44MiB；Yjs编码71982B（约0.069MiB）。
- 少量、高频位置修改：相对空载堆 **8.10MiB**；相对本次加载增长 **6.70MiB**，范围6.702–6.725MiB；Yjs编码1863130B（约1.777MiB）。
- 大量、仅加载：4000图形，相对空载堆 **42.68MiB**，范围42.683–42.735MiB；Yjs编码2947055B（约2.811MiB）。
- 大量、高频位置修改：相对空载堆 **49.03MiB**；相对本次加载增长 **6.34MiB**，范围6.320–6.348MiB；Yjs编码4758598B（约4.538MiB）。

推论：在本轮同次数、同载荷、同操作边界下，初始数据规模决定主要基线，历史修改增量没有随图形数增长40倍。不能由此推导所有编辑类型、记录ID churn或图片负载都相同。

## 估算其中多少来自撤销保留

配对估计公式：同一repeat中，`捕获组修改增长 − 关闭捕获组修改增长`，再取3次中位数。关闭捕获只作为对照，不是取消产品撤销的建议。

- 100图形、位置更新：关闭捕获仍增长1.30MiB；历史捕获额外约 **5.40MiB**，约 **189B/更新**。
- 4000图形、位置更新：关闭捕获仍增长0.82MiB；历史捕获额外约 **5.53MiB**，约 **193B/更新**。
- 100图形、2048B文本替换：捕获组增长10.42MiB，对照增长3.45MiB；历史额外 **6.97MiB**，约 **2437B/更新**。
- 4000图形、文本替换：捕获组增长10.14MiB，对照增长3.15MiB；历史额外 **6.99MiB**，约 **2443B/更新**。

50步富文本的历史成本高于500步位置历史，所以不能只按步数限制。未捕获组的剩余增长还含有效内容变化、运行时/JIT与Store有界差量缓存；不是全部为泄漏。Store的1000条diff环形缓冲与已停用的原生HistoryManager是不同机制，不能直接一起关闭。

## 清栈、回收、重新加载与重建

同一过程按顺序采样：修改完成 → 保留历史时GC诊断 → 独立记录撤销预检影响 → 清空历史 → 对已释放内容GC → 保留原CRDT身份重新加载 → 从当前业务记录新建共享树。各阶段均断言当前内容一致；原身份回收/重载检查state vector。

- 保留撤销时，显式GC没有减少编码大小；`keep`内容受到保护。
- 清空历史后，步骤归零，但这组负载的编码大小没有变化。`clear()`解除保留，不代表旧删除内容已立即回收。
- 100图形、位置负载：**1863130B → 清栈后仍1863130B → GC后77850B → 新树72100B**。
- 4000图形、位置负载：**4758598B → 清栈后仍4758598B → GC后2959058B → 新树2947074B**。
- 100图形、文本负载：**6430079B → GC后171089B → 新树170006B**。
- 4000图形、文本负载：**9305252B → GC后3046262B → 新树3045079B**。
- 以清栈后为参照，GC阶段观测到的堆下降：位置小/大组约4.67/4.79MiB，文本小/大组约6.85/6.83MiB。不能把它和文件字节节省相加。

诊断使用`Y.tryGc`和`createDeleteSetFromStructStore`。它们有导出和类型，但依赖底层StructStore/Item，缺少高层维护API的官方稳定性承诺；不能原样当作已上线方案。

额外注意：位置大组的撤销预检伴随约3MiB采样堆下降，但编码、历史范围和结构计数不变。已将预检独立成阶段，未把这段下降算作GC收益。V8表示/JIT/缓存的精确归因尚无堆快照证据。

## 维护本身的成本

当前位置负载，3次中位数：

- 释放后原地GC诊断：100图形约0.65ms；4000图形约5.53ms。
- 原身份重新加载并重建绑定：约18.4ms / 405.2ms。
- 新共享树重建并绑定：约11.8ms / 354.8ms。
- 整文档撤销预检：约56.4ms / 278.5ms；大组范围265–401ms。
- 预检结束、尚未主动GC时的堆增量：位置小/大组约14.8/62.4MiB；文本大组约109MiB。这是操作结束时的观测增量，不是瞬时峰值或总分配量。

因此，不应把重载/重建放到每次修改、每次拖动结束或固定一分钟的主线程热路径。大文档撤销的全量克隆也需要单独优化，不能用“压缩了文件”代替解决。

## 离线正确性机制检查

`tests/tldraw-yjs-compaction-research.cjs` 4/4通过：

1. 活跃历史保护旧值；clear后编码仍不变，释放后GC才减小。
2. 保留CRDT身份的GC后，迟到的独立改色仍可合并；另一端本地undo可继续保留移动结果。
3. 删除并GC的图形不会被离线旧子树更新重新显示。
4. 从JSON新建共享树后，旧客户端的颜色更新在该反例中未进入新树，证明它不能透明替代普通GC。

这里只验证小型flat-geo机制。state vector相同和4个样例不等于所有分组、图片、绑定与多设备场景的生产证明。

## 真实浏览器与IndexedDB复核

Chrome156、真实Editor、DOM、Yjs与独立IndexedDB测试库，开发构建启用跨源隔离，使用measureUserAgentSpecificMemory。最终统一为6000次位置更新、100个手势，每组一次，不能与Node的30000次直接比较。

- 100图形：整页内存从190854024B变为169234898B，约182.01→161.40MiB。
- 4000图形：整页内存从408919846B变为391088088B，约389.98→372.97MiB。
- 两组整页总量均下降，受冷启动、代码缓存、GC与开发环境影响；不能解释为修改降低Yjs内存，也不能从这些总量差值推导历史阈值。受控Node配对结果是本次方案的主要依据。
- 100图形IDB有效载荷从74592B增至429157B；4000图形从2959053B增至3313620B。等待实际事务与计数稳定后，两组每次采样均已合并为1条记录。
- 另保留早期100图形/30000次试跑：清空500步历史后，编码和单条IDB载荷仍为1866041B。说明日志合并、清栈与内容回收是不同事情。
- 所有记录的原生undo/redo栈均为0。页面操作时间包含分帧让出、GC及调度，不用于比较吞吐或帧率。

浏览器数据保留最终4个采样、早期3个采样与中止试跑说明。这里只测一次开发环境，没有正式构建、移动端、Liveblocks或稳定的模块级内存归因；IndexedDB载荷不是磁盘物理文件大小。

## 建议方案与触发阶段

业务更新继续沿现有Store→Yjs差量链路及时同步，不等待压缩窗口；本轮没有比较网络节流策略，不据此新增延迟。手势结束只更新历史预算，空闲窗口执行维护，重新加载放在打开文档时。三者使用不同的触发边界。

### 第一阶段：先限制历史保留，保持当前编辑语义

- 首版候选为 **200个完整操作＋4MiB保留旧值JSON软预算**，undo和redo一起统计，以先触发者为准。
- 只淘汰最旧完整步骤，同步清理失效标记/冲突版本索引，正确释放Yjs保留关系。不能简单shift数组，也不能释放剩余步骤依赖的共享结构。
- 基于当前实测线性估计：200步位置操作的历史额外堆约2.2MiB；文本负载会更早碰到4MiB旧值预算，约33步、历史额外堆约4.6MiB。这里不含当前内容、Store有界缓存等，是候选估算，不是实现后的验证。
- 保留最新完整操作；若单次大操作已超过软预算，应提示并单独治理大资源，不能静默拆分、取消撤销或回收仍可撤销内容。因此软预算不能当硬内存保证。
- 每个手势完成后更新轻量计数；不在每帧序列化整个文档。不要只根据图形数量或文档比值触发。

### 第二阶段：在安全空闲边界回收已释放内容

- 首版候选：手势结束、当前没有undo/redo/AI正式提交事务，且空闲约 **2秒** 时处理。2秒是交互策略初值，不是本轮测得的最优常数。
- 按已释放旧值量合并工作；例如累计约1MiB待回收载荷再启动一次，避免每丢弃一个步骤都扫描整Doc。连续编辑场景需要最大延迟和分批预算策略，不能依赖“总会空闲”。
- 先实现受控、锁版本的回收适配与保留关系验证，再讨论上线；桌面样本5.5ms不保证所有设备都能塞进一帧。
- 复用IndexedDB现有约500条更新/1000ms debounce日志整理，避免重复定时器。确认实际事务和记录数稳定后才声称完成，不能只await当前版本storeState的外层Promise。
- 收缩后的状态落盘前后验证业务快照、原CRDT身份与恢复；失败保留原数据。单条IDB日志仍可能保存旧载荷，不能当成已回收。

### 第三阶段：重载与重建放在明确生命周期边界

- 下次打开文档时正常重建本地Doc并启用GC；不要自动热替换仍有本地撤销历史的编辑器。
- 本轮回收后重建仅再省1–12KB，不足以支持增加周期性文档换代系统。
- 只有未来记录ID churn/旧根等元数据显著膨胀、回收后仍有明确收益时，再研究换代；需要备份、独立版本/房间、旧token隔离、离线旧稿恢复和缓存切换，不能直接把新Y.Doc更新合并到旧云端。
- Liveblocks服务端GC时机和物理回收比例仍未知；客户端编码减小不等于已减少云端占用。

### 验收顺序

1. 先实现历史双限额与正确释放，保持移动/颜色独立、整步冲突阻止、近期undo/redo及取消语义。
2. 复跑本轮矩阵，加入图片大值、创建删除ID churn、group/frame/binding、远端乱序和旧离线客户端。
3. 针对真实移动端和正式构建测长会话保留堆、主线程停顿与峰值，再调整200步/4MiB/2秒等候选参数。
4. 单独优化全量undo预检的复制成本，保持引用完整性检查；生产前需真实Liveblocks复核。
